# NexaPOS Lite till - tests

The Lite till (`/lite/`) is a plain-JavaScript till for old iPads (iOS 10). See `LITE-TILL-DESIGN.md`
in the release workspace for the whole plan. These are the checks that keep it safe:

| Command | What it proves |
|---|---|
| `node tests/lite/es5.test.js` | every script of the page parses as strict ES5 and uses no built-ins missing from Safari 10 (the checker is itself tested against arrow functions, `let`, template strings, classes, async) |
| `node tests/lite/core.test.js` | the join / catalog / login logic against a scripted fake server; logins are checked with real bcrypt hashes made by the app's own library (`fixtures/bcrypt_fixtures.json`) |
| `LITE_API=http://127.0.0.1:8080/index.php node tests/lite/integration.js` | the same logic against a REAL platform server: invite, join, catalog with stock summed from movements, login, a used invite refused |

`vendor/acorn.js` (MIT) is only used by the ES5 checker. `lite/bcrypt.min.js` is bcryptjs 2.4.3 (Apache-2.0, plain ES5).

`fixtures/bcrypt_fixtures.json` is generated by `test/tool/make_bcrypt_fixtures.dart` in the mobile repo
(`dart run test/tool/make_bcrypt_fixtures.dart <out.json>`).

To run the integration test locally you need the platform repo's PHP server on a fresh MySQL database
(see the platform repo's `tests/integration/run.php` for the environment variables).

| Command | What it proves |
|---|---|

| `node tests/lite/held.test.js` | Held sales: a sale set aside keeps everything on the screen (items, sale type, discount, payment choice, number, cash typed), newest first, auto-named Held sale 1, 2, 3; survives a reload, a log out and another cashier; limit of 50; odd carts are refused or tidied; takes no stock and sends nothing; opening or throwing away removes only that one, for good (12 tests, mutation-checked: 37 of 37 weakenings caught) |
| `node tests/lite/print.test.js` | The receipt, laid out like the apps' (shop, "Powered by NEXAPOS", receipt number, date as "7 Mar 2026 10:05", cashier, items as "name  qty x unit", Subtotal / Discount / TOTAL always shown, Payment with cash received and Change due / Still owed, M-Pesa called M-Pesa, Sale type, Status, thank-you and support lines, the shop's footer, the barcode); amounts carry the currency; a reprint says so; shop details with a safe fallback for a silly paper width; making a receipt changes nothing (13 tests, mutation-checked) |
| `node tests/lite/today.test.js` | "Today on this iPad" totals on the Sales tab: finished sales since the iPad's midnight (exactly midnight counts, a second before does not), split into cash / M-Pesa / online with item count; an unpaid or cancelled online payment, a sale the shop refused and one the owner removed are left out; a discount counts as the money taken; says when the iPad may have forgotten some of today (it keeps the latest 100); asking changes nothing (9 tests, mutation-checked: 23 of 23 weakenings caught) |
| `node tests/lite/reports.test.js` | Reports: which period is meant (day / month / selected period / expenses; local midnight as UTC instants and plain dates; ordinals like 12TH; either order of a period; 400-day cap; impossible dates refused) and the call that fetches the shop's report (exact request, validated answer incl. a true list, friendly words for offline / refused key / old server / unreadable answer, sales still waiting on this iPad counted) (14 tests, mutation-checked) |
| `node tests/lite/dashboard.test.js` | The dashboard: the apps' change-since-yesterday rule (nothing-to-compare cases, rounding half away from zero), the 7 local days as 8 edges (month and year ends, leap year, just after midnight), Low Stock (at or below the reorder level, every product) and Stock Value (cost x stock) from the catalog on the iPad, and the call (12 tests, mutation-checked: 55 of 57 with the two left being the control and an equivalent case) |
| `node tests/lite/barcode.test.js` | The receipt barcode is the apps' barcode: SHA-256, the 24-digit number and the Code 128 bars are compared with what the app itself produced (fixtures/receipt_barcodes.json, made from the app's own code) for sample receipts and every pair of digits 00-99 (10 tests) |
| `node tests/lite/update.test.js` | "A new version is available": the page tells a newer release apart from the one running (build label in `<meta name="lite-build">` + each script's `?v=`; error pages, login walls and empty answers never count as an update); the real page carries the label, versioned scripts and the update bar; **release guard**: fails when anything in `lite/` changed without the build label being bumped and recorded (8 tests, mutation-checked: 17 of 17 weakenings caught) |
| `LITE_API=... LITE_FAKE_PAYSTACK=http://127.0.0.1:18090 LITE_MYSQL=<mysql client> LITE_DB_NAME=<db> node tests/lite/online-integration.js` | the same flow against a REAL platform server and a pretend Paystack (platform repo `tests/integration/fake_paystack_lite.php`): initialise with the shop's payout account, own email and the Lite return page; guard accepts the pending sale and its settle; abandon/cancel; wrong amount refused by the platform; only the starting device can verify; no payout account refused; tampered settle refused |

Start the platform with `PLATFORM_PAYSTACK_API_BASE=http://127.0.0.1:18090`, `PLATFORM_PAYSTACK_SECRET_KEY=test-only`,
`NEXAPOS_IGNORE_LOCAL_CONFIG=1` and a database name that does **not** exist yet (the server creates and migrates it).

`lite/qrcode.js` is qrcode-generator 1.4.4 (MIT, Kazuhiko Arase), plain ES3/ES5.

## Releasing a new Lite version

1. Change the files in `lite/`.
2. Bump `<meta name="lite-build" content="YYYY-MM-DD.N">` in `lite/index.html` and the `?v=` of each script you changed.
3. Run `node tests/lite/update.test.js --record` (it refuses if the files changed but the label did not).
4. Upload as usual. Every iPad that has the till open then shows "A new version of NexaPOS Lite is available" within about five minutes (or as soon as the page comes back to the front); "Update now" puts a sale in progress on hold and reloads.
